# Lotto 배포 및 Compose 전환 검토

## 보존할 기능

기존 배포 PR의 목적은 자동 GHCR 게시, 컨테이너 포트와 healthcheck 정합성, 기존 프록시 네트워크 연결과 재시작 정책을 재현하는 것이었습니다. 현재 main은 자동 게시·포트 4100·healthcheck를 더 엄격한 의존성/이미지 검사 및 비특권 런타임으로 대체했습니다. 이전 PR 전체를 병합하거나 과거 Dockerfile을 복원하지 않습니다.

## 현재 코드에 맞는 설치 순서

1. `npm ci` 후 저장소 보안·회귀 검사를 실행합니다. CI 검사 및 게시 절차는 `security.md`를 따릅니다.
2. 승인된 릴리스의 SHA 또는 digest와 플랫폼을 확인합니다. `latest`라는 이름만으로 현재 실행 이미지와 같다고 판단하지 않습니다.
3. 기존 프록시 upstream, 연결 네트워크, 실행 환경변수 이름, 현재 컨테이너의 포트 바인딩과 재시작 정책을 기록합니다. 비밀값은 문서나 Git에 넣지 않습니다.
4. 지도 JavaScript 키는 실행 환경에서 전달하고 등록 도메인을 제한합니다. 서버 전용 키로 대체하지 않습니다.
5. 별도 후보 컨테이너에서 healthcheck와 실제 지도 SDK·판매점 데이터·페이지 동작을 확인한 뒤, 승인된 전환 절차로 프록시를 바꿉니다. 운영 컨테이너를 먼저 정지하는 절차를 기본값으로 삼지 않습니다.
6. 전환 전후 이미지 digest, 응답, 관찰 결과를 기록하고 복구 대상을 유지합니다.

## 과거 Compose fragment를 그대로 쓰지 않는 이유

과거 예제는 `4100:4100`으로 모든 호스트 주소에 직접 포트를 열고 기존 컨테이너를 먼저 중단하도록 안내했습니다. 현재 확인한 운영 형태는 앱에 호스트 포트를 직접 게시하지 않고 같은 사설 Docker 네트워크의 별도 프록시를 통하는 방식입니다. 이 예제를 그대로 가져오면 다른 서비스의 호스트 포트와 충돌하거나 기존 접근 제한을 우회하고 순단을 만들 수 있습니다.

Compose로 선언적 관리를 추가하는 기능 자체는 유용하지만 아직 별도 마이그레이션 작업입니다. 다음을 확인하기 전에는 실행 가능한 배포 파일을 추가하지 않습니다.

- 기존 Compose 프로젝트의 소유권과 서비스 이름을 확인해 중복 앱을 생성하지 않기
- 정확한 external network 및 프록시 upstream 식별자를 보존하기
- 앱의 직접 `ports` 게시를 추가하지 않기 (`expose`는 호스트 게시가 아니지만 접근 제어도 아님)
- 새 digest와 런타임 환경변수 매핑, 기존 restart 정책을 보존하기
- 이미지 healthcheck를 활용하고 프록시 전환·복구 절차를 함께 검증하기

단순 `docker compose config` 성공은 운영 네트워크·프록시·도메인·롤백 동작의 검증이 아닙니다. 이 문서는 배포 실행이나 Compose 전환 완료를 의미하지 않습니다.
